How to diff a JSON config against its YAML equivalent

Compare two configs in different formats by meaning — and catch the type changes that break parsing.

You're migrating a service's config from JSON to YAML. Or you keep the "same" settings in two formats — a JSON file the app reads and a YAML file a tool generates — and you want to be sure they still agree. How do you check that the migration didn't quietly change a value?

You can't git diff them: the files share no lines. You can't diff -u them either — one is {"port": 8080} and the other is port: 8080, so a text tool sees two completely different files even when they mean exactly the same thing. Most semantic diff tools don't help here either: they compare JSON to JSON, or YAML to YAML, but not one against the other.

Diff by meaning, across formats

confdiff parses each side into a plain data tree first, then compares by key and value — so the two sides don't have to be the same format. Give it a JSON file and a YAML file and it just works. Here the only real difference is the log level; the keys are in a different order and one side is JSON, the other YAML:

config.json

{
  "server": {
    "host": "0.0.0.0",
    "port": 8080,
    "tls": true
  },
  "logging": { "level": "info" },
  "features": ["search", "export"]
}

config.yaml

logging:
  level: debug
server:
  port: 8080
  host: 0.0.0.0
  tls: true
features:
  - search
  - export
$ confdiff config.json config.yaml
~ logging.level  "info" => "debug"

One line, the real change. The reordered keys and the format difference produce nothing. If the two files really do mean the same thing, you get the answer you want:

$ confdiff config.json config.yaml
no semantic differences   # exit code 0

That makes it a one-command migration check: convert your JSON to YAML, run confdiff on the pair, and a clean exit code proves nothing changed in the move. The same works for TOML — compare a config.json against a config.toml and you get one unified, path-addressed diff.

The type change a text diff can't catch

Here's the subtle bug that cross-format work introduces, and the reason to diff by meaning. In JSON, "port": 8080 is a number. If the YAML (or an .env, or a Helm value) quotes it as port: "8080", it's now a string. Same characters, different type — and plenty of config loaders will reject "8080" where they wanted an integer, or compare it wrong. confdiff flags exactly that:

$ confdiff config.json config.yaml
~ server.port (type)  8080 => "8080"

The (type) marker tells you the value looks the same but the type changed — the kind of thing that passes a text diff (or a human skim) and breaks at runtime.

When you want loose comparison. For .env and .ini files, everything is a string anyway, so 8080 and "8080" are the same thing to you. Add --loose and confdiff compares scalars loosely — "8080" equals 8080, "true" equals true — so you only hear about differences that actually matter:

$ confdiff config.json config.yaml --loose
no semantic differences

Forcing a format when there's no extension

confdiff picks the parser from the file extension. When you're piping data or a file has no telling extension, name the format explicitly — either for both sides or independently:

$ cat a.env | confdiff - b.env --format env      # both sides .env
$ confdiff old.txt new.txt --format-a json --format-b yaml

Everything else stays the same: path globs to --ignore expected differences, a --json mode with RFC 6901 JSON Pointers for tooling, and clean exit codes (0 equal, 1 differences, 2 usage error) so a migration check can gate a CI job.

Try it on your own two files

Paste a JSON config on one side and its YAML on the other in the confdiff playground — set the two format dropdowns independently. It runs entirely in your browser, so nothing you paste is uploaded. Or run it with zero install:

npx github:esperanza-volkov/confdiff config.json config.yaml

No Node? Run the container: docker run --rm -v "$PWD:/work" ghcr.io/esperanza-volkov/confdiff a.json b.yaml
